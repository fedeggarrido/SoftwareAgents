# AsyncAPI protocol contract

FEAT-001 adds the read-only audit messages on the existing WebSocket ingress:

- Client: `RequestAuditLog` = `{ type: 'requestAuditLog', projectId: string, requestId: string }`. Malformed requests with non-string or missing identifiers are ignored.
- Server: `AuditLogSnapshot` = `{ type: 'auditLog', projectId, requestId, status, entries, totalValid, truncated, corruptLines, excludedCount }`. Replies are point-to-point and echo both identifiers; clients must discard stale replies after a Project change or a newer request.
- Status is `ok`, `empty`, `read_error`, `denied` or `unknown_project`. Existing connection privilege is checked before Project binding. Unprivileged connections receive `denied`; a Project other than the server-bound Project receives `unknown_project`. These responses and `read_error` have `entries: []`, `totalValid: 0`, `truncated: false`, `corruptLines: []` and `excludedCount: 0`, without error details.
- Only the bound Project log is read, never the machine log. At most 500 entries are returned, newest first with descending line-number ties. `totalValid`, `corruptLines` (1-based line numbers) and `excludedCount` cover the entire file. Blank or missing logs are `empty`; a nonblank log containing only corrupt or excluded entries is `ok`.
- `AuditViewEntry` includes `line`, `occurredAt`, `actorType`, `actorId`, `action`, `resourceType`, `resourceId`, `policyDecision` (`outcome`, `reason`) or null, `riskLevel`, `outcome` (`status`, `reason`, `detail`, `tier`, `executor`, `model`, `code`), `taskKey` and `executionId`. Optional display values normalize to null; all displayed text uses existing audit redaction. `inputHash` and raw corrupt-line content are never transmitted.
- No branch records an audit event or writes a log. This adds no permissions, routes, export or mutation operations.

> Read before adding or changing any ServerMessage/ClientMessage. Moved verbatim from CLAUDE.md.

## AsyncAPI Protocol Contract

`core/asyncapi.yaml` is the contract. Pinned to **3.0.0** because `@asyncapi/modelina@5.10.1` declares `supportedVersions: ['3.0.0']` only; bumping to 3.1.0 produces `export type Root = any`. Revisit when Modelina ships 3.1.0 support.

- **39 ServerMessage variants** (server → client): agent lifecycle, agent activity, sub-agent activity, team + context usage, assets, settings + workspace, company, executor availability, work domain events, diagnostics.
- **27 ClientMessage variants** (client → server): lifecycle (`webviewReady`, `launchAgent`, `focusAgent`, `closeAgent`), layout (`saveAgentSeats`, `saveLayout`, `exportLayout`, `importLayout`), settings (`setSoundEnabled`, `setHooksEnabled`, `setWatchAllSessions`, `setAlwaysShowLabels`, `setHooksInfoShown`, `setLastSeenVersion`), discovery + assets, company, executor availability (`setExecutorEnabled`, `setExecutorLevels`, `requestExecutorState`), diagnostics.

SA-035 extends the existing `boardState.quota` with optional typed `CapacitySnapshot` observations (source, confidence, windows, epoch-second timestamps); message counts were 35/24 then. Legacy quota fields stay compatible.

SA-029 adds work domain events to the office: `workSnapshot` (the bound Project's tasks + unresolved structured Human Decisions + `lastEventId`, read fresh from the WorkStore in the `webviewReady` handshake, `source` ok/missing/unreadable) and `domainEvent` (live notices). The `DomainEvent` union and its closed kind catalog live in `core/src/domainEvents.ts`, type-checked against the generated wire payload. `server/src/domainEventRelay.ts` polls `domain_events` READ-ONLY (never through `openWorkStore`, whose sweeper writes) with an in-memory cursor: history before start is state (served by the snapshot), not news; nothing is acked or persisted, so a lost notice is recovered by the next snapshot. Each transition yields `task.state_changed` plus the kinds the state machine makes certain (leased, execution started/finished, review/qa requested, quota.waiting, human.decision.required/answered — answered only when the log names the decision). `executionId` is attributed only within the transition's own lease window; reasons and actors never leave the server. `task.created`/`quota.exhausted` are in the catalog but no WorkStore writer records them yet. Standalone only; broadcasts go through the AgentStateStore.

SA-087 adds the Executor availability contract (design: docs/design/executor-toggles.md): the closed catalog `core/src/executorCatalog.ts` (`claude`, `codex`; no local model per ADR-0004) mirrored by the `ExecutorId` enum, `webviewReady.capabilities` (`executorControls`), `executorState`/`executorToggleResult` and `setExecutorEnabled`/`requestExecutorState`. Capability-gated: only clients that announce `executorControls` receive `executorState`. `server/src/executorState.ts` validates the client messages at runtime and builds a read-only snapshot (Operator `allowedExecutors`, SA-036 gate, SA-084 tiers; installation/auth stay `unknown` until SA-089). `canManage` is per recipient (privileged connections only). Standalone only, like the company controls.

SA-088 makes `setExecutorEnabled` a durable Operator authority change through ONE service, `server/src/executorAvailability.ts`: privilege (before any Project id) → server-bound Project → `evaluatePolicy('change_executor_availability')` (human gate at every level) → machine admission lock (no worker admits meanwhile) → whole-file config lock → strict re-read + CAS on `operatorRevision` (canonical SHA-256 of the Operator block) → durable intent marker `~/.pixel-agents/executor-availability/<project>.pending.json` → audit intent (failure aborts) → persist only `allowedExecutors` membership (unique tmp, fsync, rename, verify) → audit result → clear marker → `applied`. Anything else answers `failed`/`rejected` with its code, never `applied`. While a marker exists the snapshot reads `recovery_required`, toggles are refused and every worker fails closed until `pixel-agents executors recover <project>` audits what the config actually holds. Workers re-check the Operator block inside machine admission and drop runs whose policy changed since they started. A toggle never creates a Project or repairs an invalid policy. After a change each capable connection re-reads its own snapshot (`store.notifyExecutorStateChanged`).

SA-089 fills the snapshot's technical facts from `server/src/executorProbes.ts`: per Executor, `--version` (≥ the minimum version tested in this repo: Claude 2.1.220, Codex 0.160.0), the help text listing every flag its executor passes, and auth only through a subcommand the CLI's own help lists (`claude auth status --json` → `loggedIn`; `codex login status`), so an older CLI can never read it as a prompt. Probes: async spawn, no shell, cwd tmpdir, stdin closed, 3 s timeout, 128 KB output cap, binaries resolved exactly as the Executors do (an invalid Operator override is `missing`, never a fallback search). `ExecutorMonitor` caches per resolved binary (one probe per binary however many clients), refreshes enabled Executors every 60 s, backs off to 5 min on failure, TTL 120 s (`probe_stale`); the standalone CLI starts it (`startExecutorMonitoring`) and pushes a snapshot when a fact changes; disabled Executors are not probed. Only parsed facts leave the module — never paths or CLI output. `not_installed`/`unsupported_version`/`auth_required` and an unproven installation block eligibility; unobserved, unknown auth and stale only flag it (shared `launchBlock`, SA-090).

SA-090 (selection and drain): the worker probes its own candidates before admission (`observeExecutors`), excludes Operator-only problems and waits on unproven ones, revalidates authority + fresh probe + quota under machine admission right before the executor starts, after the slow worktree preparation (that check is the frontier: before it a change invalidates the run, after it a toggle drains, never cancels), and turns "no eligible executor" into ONE deduplicated WAITING_HUMAN Human Decision per Project/scope/cause that closes itself when a run of that scope is admitted again. See docs/executor-selection.md.

SA-092 (levels per Executor): Operator `executorLevels` (`{claude?, codex?}: ModelTier[]`) narrows which `modelTiers` levels each Executor may run — absent = every catalog level, `[]` = blocked at every level. Changed by `setExecutorLevels` through the SAME `executorAvailability.ts` service (privilege, binding, policy, admission + config locks, CAS, marker, audit `kind: levels`, recovery); levels must be a subset of the Executor's `catalogLevels` (never widens the catalog) and allowing them all deletes the key. Selection excludes the candidate as `level_disabled` — an Operator exclusion, so it never triggers a tier fallback (quality is kept) and an all-excluded tier blocks as `no_allowed_level`. `ExecutorAvailability.levels` is the effective set; optional `catalogLevels` is what can be allowed (its absence = server without level controls). Answered with `executorToggleResult`.

**Config writers cooperate (SA-088)**: every write of `~/.pixel-agents/config.json` takes `withConfigLock` (lease lock in `~/.pixel-agents/locks/`, shared algorithm in `server/src/leaseLock.ts`, also used by discovery). Legacy `writeConfig` refuses to write over a file it cannot parse (it used to persist defaults over it) and three-way merges `projects`: on-disk entries win unless this caller changed that Project since its `readConfig()`, so a stale settings write never reverts an Operator change. Project bindings read `softwareagents/runs` under the Git common dir; legacy boards retain `board.runsDir`. Usage tokens alone cannot establish account capacity.

Both unions use `oneOf` with `discriminator: type`. Every concrete message sets `additionalProperties: false`.

`core/src/messages.ts` is generated by `scripts/generate-messages.ts` invoking `@asyncapi/modelina` with custom constraints (`propertyKey` preserves `type`/`status` field names; `constant` inlines `const` literals). The file has an auto-generation banner. **CI runs `asyncapi:generate` then `git diff --exit-code core/src/messages.ts` — any non-empty diff fails the build.**

## Features panel (FEAT-002)

- Client: `RequestFeatures` = `{ type: 'requestFeatures', projectId: string, requestId: string }`.
- Server: `FeaturesSnapshot` = `{ type: 'featuresSnapshot', projectId, requestId, status, reason, features: FeatureRow[] }`. Replies are point-to-point and echo both identifiers. Clients discard replies for a different selected Project or obsolete request.
- The request uses exactly the `requestAuditLog` guard: existing connection privilege first (`denied` otherwise), then the server-bound selected Project (`unknown_project` otherwise). It adds no permissions, tokens, actor flags or ingress routes. Neither rejection returns feature data.
- Status is `ok`, `empty`, `denied`, `unknown_project` or `read_error`. Only a successful read with no registered features is `empty`. Rejections, errors and empty results carry `features: []`. Only `read_error` has a non-null reason, restricted to `unavailable`, `schema_incompatible`, `query_failed` or `invalid_data`; exception messages and traces never leave the server.
- `FeatureRow` contains only `key`, nullable `title`, `state` (`merged`, `ready_to_merge`, `in_review`, `in_design`, `in_development`, `unknown`), nullable `rawStatus` for unknown persisted states, nullable `progress {done,total}`, nullable `currentTask {key,step,others}` (step `develop`, `review`, `qa` or null), `gates [{kind,task,expired,command}]`, nullable `integration {branch,sha}` (abbreviated SHA or null), and nullable `lastActivityAt`. Progress null means no imported tasks. Gates use `spec_approval`, `requirements_questions`, `design_questions`, `human_decision`, `waiting_human`, `quota` or `qa_not_tested`; task is nullable. `merged` requires a completed imported DAG and local Git ancestry evidence for the persisted integration HEAD; refs and objects are read without processes or writes.
- This is a read-only WorkStore projection. Commands are display text for manual use in the operator's terminal; answer commands retain the literal `<fichero-de-respuestas>` placeholder. There are no approve, answer, run, resume, stop or cancel messages or controls. Reads do not write WorkStore, audit, Git or Brain state or launch processes.
- Each `FeatureRow` also requires a closed `cost` object: `executions` (total ledger executions), `costKnown` (executions with known cost), nullable `costUsd` (sum of known USD costs), nullable `costPerDoneTaskUsd` (cost divided by all DONE tasks of the feature, including DESIGN/REQUIREMENTS), and nullable `cacheHitRate` (the ledger aggregate over executions with both token counters). Null means «sin datos»; known zero remains zero. Partial cost is derived from `0 < costKnown < executions`, with coverage `costKnown de executions`. The existing read-only transaction reads only the selected Project's ledger and attributes entries by exact feature key; unassigned entries count nowhere. A v15 database without `usage_ledger` produces zero executions and null figures. Malformed ledger data fails closed with `invalid_data`; non-finite aggregate figures become null. No ledger payload, model, quota, prompt, path or configured price is exposed, and no extra request or endpoint is added.
- All projection objects reject additional properties. Producers must sanitize allowed free text too: prompts, model outputs, operator answers, stdout/stderr, full Review/QA reports, absolute paths (including `doc_path`), PIDs, process identities, remote URLs and secrets must never be transmitted. Consumers render titles and other free text as escaped text, never interpreted HTML or Markdown. Schema validation alone cannot sanitize string contents or enforce authorization; the server reader/handler must enforce those requirements.
